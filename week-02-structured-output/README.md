# Week 02 — Structured Output and AI Contracts

An AEM diagnostic assistant that returns a **validated typed object**, not prose, and
exposes it over HTTP.

```
contracts.py   Severity, AemDiagnostic (the result contract), DiagnosticRequest (the input contract)
service.py     INSTRUCTIONS, diagnose(context) -> AemDiagnostic, DiagnosticUnavailable
part_b.py      script: one diagnosis, printed as object and as JSON
part_c.py      script: consuming the object — escalation, actions, a rejected bad payload
api.py         FastAPI: POST /diagnose, a handler that only calls the service

```

## Why structured output is safer than parsing prose

A prose answer has no contract. "The bundle is Installed because commons-lang3 3.20 is
missing — this is high severity" contains everything the caller needs and offers no way
to *get* any of it: the caller has to search strings, and the string it searches changes
with the model, the temperature, the phrasing of the question, and the day. Every
consumer re-implements the same brittle extraction, and each one fails differently.

With a schema, the extraction happens once, at the boundary, and the result is either a
valid `AemDiagnostic` or an explicit failure. `part_c.py` shows what that buys:

```python
ESCALATE = {Severity.HIGH, Severity.CRITICAL}
escalate = diagnostic.severity in ESCALATE
```

That is set membership on enum members. It cannot be defeated by "high-ish", by
capitalisation, by the model calling it "Sev-1", or by a sentence that mentions the word
"critical" while saying the opposite. The escalation decision is no longer a text match;
it is a type.

The second gain is the failure mode. Prose parsing degrades *silently* — a regex that
stops matching returns nothing and the caller carries on with a default. A schema
violation raises, loudly, at the boundary, before any downstream system sees the value.

## What schema validation guarantees — and what it does not

**Guaranteed, by the decoder.** With strict structured output the model physically cannot
emit tokens that break the shape: required keys are present, types match, unknown keys
are impossible, and **enum members are enforced** — `severity` genuinely cannot come back
as `"sev-1"`. Guarantees you intend to *depend on* belong in enums and types.

**Not guaranteed by the decoder — validated after the fact.** Range and length keywords
(`min_length`, `ge`, `le`) are sent in the schema but are hints to the model, not decoder
constraints. Pydantic catches violations client-side *after* the response arrives, which
means `client.responses.parse()` can itself raise `ValidationError` from inside. A
wrapper that only checks for `None` is incomplete — `service.py` therefore catches both
and re-raises one application exception:

```python
except ValidationError as e:
    raise DiagnosticUnavailable("model returned data outside the contract") from e
```

**Not guaranteed at all:** that the values are *true*. Validation is a statement about
form. See the next section.

Two contract decisions this week that follow from the distinction:

- **`evidence` keeps `min_length=1`.** The caller always supplies the context, so at
  least one real citation is always available; requiring it costs nothing and makes an
  unsupported diagnosis harder to produce.
- **`suggested_actions` is deliberately left unconstrained.** A required non-empty list
  is an instruction to invent a remediation step when the context supports none —
  schema-shaped hallucination, requested by the schema author. The empty case is instead
  rendered explicitly by the consumer:

  ```python
  else:
      print(" none - the context does not support a remediation step")
  ```

- **Field order is generation order.** `confidence` is declared last so the model scores
  its certainty *after* committing to a cause, not before.

## Why syntactically valid structured output can still be factually wrong

Validation moves the failure from *unparseable* to *parseable and possibly wrong*. Every
field can satisfy every constraint while the diagnosis names the wrong bundle, cites a
log line that does not exist, or confidently explains a version range that was never in
the context. The schema constrains the shape of the answer; nothing in it constrains the
answer to reality.

The clearest illustration from this week is the `confidence` field. On the
bundle-resolution context the model returned **`severity: high`, `confidence: 0.99`** with
a correct diagnosis — but that 0.99 is a *self-assessment generated by the same process
that produced the answer*, not a calibrated probability. A wrong answer is available at
0.99 just as cheaply. The field is useful as an application signal (route low-confidence
results to a human, log the distribution, alert when it drops) and worthless as evidence
that the content is right.

What actually reduces factual error is not the schema but the grounding around it: the
instructions require every part of the diagnosis to come from the supplied context, and
`evidence` is described as *verbatim* lines from that context, which makes fabrication
checkable — a reviewer can diff the evidence against the input. That is a mitigation, not
a guarantee, and it is why the interesting engineering at this boundary is upstream
(context quality, grounding) and downstream (validation, escalation), not in the model
call itself.

## The service boundary, and the status codes

`api.py` keeps the HTTP layer thin on purpose — the handler's whole body is
`return diagnose(request.context)` inside one `try`. The model call, the prompt, and the
failure translation stay in `service.py`, so the same function is callable from a script,
a test, or a future agent loop with no web server involved.

Three failure modes, three answers:

| Failure | Status | Who produces it |
| --- | --- | --- |
| Empty or malformed request body | **422** | Nobody — `Field(min_length=1)` on `DiagnosticRequest` |
| Model refused, truncated, or returned data outside the contract | **502** | `HTTPException(502)` on `DiagnosticUnavailable` |
| Anything unanticipated | **500** | FastAPI's default |

502 rather than 500 is the considered choice: the caller did nothing wrong and the
failure is in an upstream dependency, so a retry is reasonable. Returning 200 with an
empty diagnostic would be worse than either — it launders a failure into data that looks
valid.

One Pydantic declaration now serves three consumers: it constrains the model's decoding,
validates the response, and publishes the schema at `/openapi.json` — where `severity`
appears as a four-value string enum and `confidence` carries `minimum: 0` /
`maximum: 1`.

## The same contract as a Java DTO

A Java consumer of `/diagnose` would deserialize into a record — generated from that
OpenAPI schema, or written by hand:

```java
public enum Severity {
    @JsonProperty("low")      LOW,
    @JsonProperty("medium")   MEDIUM,
    @JsonProperty("high")     HIGH,
    @JsonProperty("critical") CRITICAL
}

@JsonIgnoreProperties(ignoreUnknown = true)
public record AemDiagnostic(
        @NotBlank String summary,
        @JsonProperty("likely_cause") @NotBlank String likelyCause,
        @NotNull Severity severity,
        @NotEmpty List<String> evidence,
        @JsonProperty("suggested_actions") List<String> suggestedActions,
        @DecimalMin("0.0") @DecimalMax("1.0") double confidence) {
}
```

The mapping is close, and the places it is *not* close are the instructive part:

| Pydantic | Java |
| --- | --- |
| `BaseModel` | `record` (immutable, value-equal) + Jackson for JSON binding |
| `Field(min_length=1)`, `ge`/`le` | Bean Validation annotations — `@NotEmpty`, `@DecimalMin`/`@DecimalMax` |
| `Severity(str, Enum)` with lowercase values | `enum` with `@JsonProperty` on each constant (Java constants are uppercase by convention; without this, or `ACCEPT_CASE_INSENSITIVE_ENUMS`, deserialization fails) |
| snake_case fields | `@JsonProperty` per field, or a global `SNAKE_CASE` naming strategy |
| Unknown fields ignored by default | `@JsonIgnoreProperties(ignoreUnknown = true)` — Jackson's default is the opposite, it throws |
| `Field(description=...)` steers the model *and* documents the API | Javadoc — documentation only; nothing reads it at runtime |

**The real difference is when validation runs.** Pydantic validates *during
construction*: if `model_validate` returns, the object satisfies the contract, and there
is no window in which an invalid `AemDiagnostic` exists. Jackson deserializes first and
Bean Validation runs as a separate step against an already-constructed object — a
`Validator` call, or `@Valid` on a Spring/JAX-RS parameter — so an invalid instance does
exist in between, and if nobody invokes the validator, nothing is checked. The Java
equivalent of Pydantic's guarantee is a compact constructor that throws:

```java
public AemDiagnostic {
    if (confidence < 0.0 || confidence > 1.0) {
        throw new IllegalArgumentException("confidence out of range: " + confidence);
    }
}
```

The other difference worth naming: Pydantic raises **all** violations at once. The bad
payload in `part_c.py` (`evidence: []` *and* `confidence: 1.4`) is reported as two errors
in a single `ValidationError` — `too_short` and `less_than_equal` — which is Bean
Validation's `Set<ConstraintViolation<?>>` behaviour, not a throwing constructor's
fail-fast one. Pick deliberately: fail-fast for invariants the type must never violate,
collected violations for anything a human has to fix.
